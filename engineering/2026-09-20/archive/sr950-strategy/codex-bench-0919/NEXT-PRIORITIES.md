From 15.82, reaching 17 requires about 7.5% more throughput. That is a numerical gap, not evidence of a consistent floor. Native prompts differ in speculation acceptance, shared-host conditions vary, and a 4K fixture is not representative of a deep conversation. The most recent separate production controls drifted roughly 3.2%; balanced same-process A/B is the primary evidence.

1. **Main-model matrix and scheduling work: largest remaining cost.** A saved short target CPU graph attributes 42.253 ms to expert matrices and 35.581 ms to dense matrices; 32.473 ms of the latter is Q8_0. The three 4096-by-2048 attention projections together account for 10.244 ms in that sample. Full target graph phases are about 138 ms per verification cycle after the MTP change. These are attribution measurements, not removable time. Production already uses packed x16 Q8, multi-token Q8 batches, tuned 16-row chunks, Q5 compact kernels, and the ordered-K special case for narrow 24-output projections. Merely enabling Q8 batching is not a new opportunity. Audit the actual packed critical path and task distribution, then require exact standalone output and representative four-socket graph gains before another full-model window. Do not repeat the unsuccessful Q4 batching/clamp-fusion experiments without a new mechanism. See matrix-bottleneck-audit.json and the frozen CPU build provenance.

2. **Draft graph preparation: smaller, clearly measured recurring cost.** The new path leaves 3.349 ms of draft preparation per steady cycle: 1.509 ms for catch-up and 1.830 ms for the first prediction; the second prediction reuses its graph. The context currently retains one previous graph, and alternating catch-up/prediction shapes force rebuilds. A separate cached plan for each role is a possible next design, not a built or validated optimization. It must handle scheduler allocations and refresh all memory-context pointers. Eliminating every preparation millisecond would still be only a few percent; this alone does not establish 17+.

3. **Deep-context pooling and indexing: most context-sensitive opportunity.** Wider pooling reduced a matched long sample from 54.714 to 24.284 ms. Cached pooled-key results remain unbuilt; GGML_GLM5N_KPOOL_REUSE is graph reuse, not a pooled-result cache. Correct handling of append, partial pools, rollback, overwrite, sequence sharing and restore is required. The long sample also has substantial custom-operation time that may include waiting, so do not label all of it useful reduction work or add it to pooling savings. Any new long-context gain must be measured independently; the old +50% unfused projection is not remaining upside.

4. **Consistency and responsiveness.** Resolve the existing cached/fresh output discrepancy, and keep benchmark requests isolated with request-owned token accounting. Prompt reuse can greatly improve time to first token but is not a decode-throughput claim. Avoid stripping useful Codex tools, skills or context merely to improve the fixture. A distribution across short coding, explanation and real long-context work is required before claiming consistent 17+.
