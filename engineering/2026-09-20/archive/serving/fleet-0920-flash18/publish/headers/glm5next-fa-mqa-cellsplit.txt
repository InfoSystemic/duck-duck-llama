GLM-5.3-Flash (glm5next) CPU library, step 4 of 6: cell-split MQA flash attention for short query batches. Revision 2.
DEPLOYED 2026-09-20. CHANGES NUMERICAL OUTPUT (toward the float64 result). GGML_F18_FEATURES bit 0, default off.
Apply after glm5next-pool-result-cache.patch (or after glm5next-kpool-wide.patch; the hunks do not overlap).

What the stock kernel does. With an F16 KV cache, ggml_compute_forward_flash_attn_ext_f16_one_chunk accumulates V in an FP16
buffer (VKQ16, ggml_vec_mad_f16). Over ~2,000 cells each addend is near or below the accumulator's rounding step, so the small
terms are dropped. It also walks the whole cache once per query-head row, converts Q to F16 for the dot product, and converts
each K/V row again for every head and query. This code is identical in upstream llama.cpp (checked at b23efaa2).

What this kernel does (absorbed MLA is MQA: one 512-wide K/V head, V aliases K, one f16 mask row per query):
  the CELLS are dealt to the workers in round-robin blocks of 64, by cell index, whatever the masks say. Pass A: every worker
  converts its K tiles to F32 once (16x16 AVX-512 transpose network), computes the masked scores of all query-head rows with one
  GEMM per tile and keeps each row's maximum. Barrier; the global row maxima are the maxima over workers. Pass B: softmax
  weights against the global maximum, V accumulation with a second GEMM, the weight sum of each row kept as a running DOUBLE.
  Barrier; per-row reduce. Everything is F32 or wider.

Why revision 2. Revision 1 let every worker take a slice of the cells that ANY query of the batch could see. That made the
summation order of one query depend on which other queries shared its batch, so a verified token's numbers depended on its draft
companions: with constant-shape (padded) draft batches the greedy text alternated between two outputs from run to run. Fixed
cell blocks make the result a function of the query alone; a float per-tile weight sum still left 1.9e-9, hence the double.
  tools/fa_mqa_invariance_check.cpp: a query computed alone and inside 3-query batches: BIT-IDENTICAL (8 trials).
  Full model, window w4: three draft-loop modes, 11 warm runs, ONE text hash (424f201528); the same hash in windows w5, w6 and
  in production after every later revision.

Because the stock kernel is ~1% off, generated text differs from the 09-19 production: 2 of 10 short factual prompts gave the same
24-token string, and token log-probabilities moved by up to 0.46 on a 7K-token prompt. Byte parity with the stock kernel is
therefore NOT the gate for this patch; the float64 comparison is. All later patches in this series ARE gated on byte parity
with this one.
