# GLM-5.3 fast dev loop + 2026-09-01 measurements

Companion to `../../GLM53-MAX-TOKS-PLAN.md`. Everything here is reproducible from-session.

## The dev loop (why iteration was slow, and the fix)

A full GLM-5.3 load is ~20 min: 436 GB from the SATA SSD at ~330 MB/s, then a repack
pass into node-local memory. Kernel and scheduler work cannot iterate at that cadence.

**Truncated dev model.** `/dev/shm/make_trunc_glm.py N OUT` writes a GGUF containing
only `blk.0..N-1` plus embeddings/output with `block_count=N`. The 8-layer file
(3 dense + 5 MoE, 33.6 GB) is at `/dev/shm/glm-dev/glm53-q4kxl-8L.gguf` and loads in
about a minute. Per-layer costs (all-reduce, barriers, expert streaming) are identical
to the full model, so relative speedups transfer; absolute tok/s does not (fixed per-token
costs - lm_head, sampling - are a larger share). Use *differences* between 8- and 16-layer
runs to isolate per-layer cost from per-token cost. Output text is garbage by construction;
never use it for quality. Keep `/dev/shm` light before a full-model load (628 GB peak).

Launch with the production script and overrides:
```
GLM_SR950_CONFIG=.../model.glm53-q4.env GLM_MODEL=/dev/shm/glm-dev/glm53-q4kxl-8L.gguf \
GLM_SPEC_TYPE=none ./launch-glm-sr950.sh 18095
```

**Profilers (both compiled into the production binary):**
- `GGML_CPU_NUMA_PROFILE=2` -> `META_NUMA_PROFILE graph=.. subgraphs=.. main=.. reduce=..`
  for the first 16 graphs: subgraph count and main-vs-reduce split per token.
- `GGML_CPU_OP_PROFILE='*' GGML_CPU_OP_PROFILE_ARM_FILE=/tmp/glm-op.arm
  GGML_CPU_OP_PROFILE_COUNT=1200` -> per-op wall time per device subgraph, armed by
  touching the file mid-request. `COUNT` is in *subgraphs per device*; a token is
  ~4 devices x ~200 subgraphs, so the default 8 captures a single dense layer (the trap
  that produced the "attention dominates" reading in `llama-llama-duck`).
- `/dev/shm/glm-dev/agg_profile.py <log> <node>` aggregates by category
  (routed experts / attention / shared / other ops).

**Harness:** `llama-llama-duck/tools/decode_bench.py` (server-reported
`predicted_per_second`, fixed prompts, temp 0, cache off). Driver:
`/dev/shm/glm-dev/run_baseline.sh <label>` = warmup, profiled raw token, then
raw / n2p0 / n4p0.6 x {prose, code, structured, novel} x 2 reps at 160 tokens.

## Kernel micro-benchmark (`/dev/shm/glm-dev/kern/kbench16.cpp`)

Links the fork's `libggml-cpu` directly. Random Q4_K rows, one q8_K activation,
16 OpenMP threads pinned to node 0 (`OMP_PROC_BIND=true OMP_PLACES=cores numactl -N0 -m0`),
233 MB working set (65,536 rows x 6144), best of 5. Run while the full model was
loading in the background (page-cache traffic on all nodes), so treat as lower bounds.

| kernel | layout | aggregate GB/s | per core |
|---|---|---:|---:|
| upstream `ggml_gemv_q4_K_8x8_q8_K` (AVX2) | 8 rows x 8-byte interleave | 94.4 | 5.9 |
| plain `ggml_vec_dot_q4_K_q8_K` (AVX2) | native | 92.2 | 5.8 |
| **new `gemv_q4_K_x16_q8_K` (AVX-512 VNNI)** | 16 rows x 4-byte lanes | **98.5** | 6.2 |
| same, L2-resident (compute bound) | | **400** | 25.0 |

Reading: on contiguous rows every kernel saturates the socket (~95 GB/s measured
ceiling). The VNNI kernel's value is 4x compute headroom (batched verify, SMT, smaller
per-thread chunks), not batch-1 streaming. So the real-graph loss is scheduling and
bytes, not arithmetic - which is what the plan's Phases 1-3 attack.

New layout (per 16 rows per 256-value super-block, 2368 B = 4.63 bpw):
```
struct block_q4_K_x16 { ggml_half d[16], dmin[16]; uint8_t scales[8][16], mins[8][16];
                        uint8_t qs[2048]; /* [j:4][i0:8][row:16][t:4] = native byte 32j+4i0+t */ };
```
Kernel: per 64-byte load, `lo = v & 0xF`, `hi = (v >> 4) & 0xF`, two `vpdpbusd` against
`set1_epi32(y[64j+4i0])` / `set1_epi32(y[64j+32+4i0])`, 4 independent accumulators, per
sub-block `vpmulld` by the 6-bit scales, mins via `bsums`, one fp16->fp32 epilogue per
block. Q5_K adds one 64-byte `qh` load per 4 positions reused for all 8 sub-blocks;
Q6_K uses two `ql` + one `qh` load per 4 positions; Q8_0 stores weights biased +128 as u8
and subtracts `128 * sum(y)` once per block.

## Results so far (evening)

Kernel micro-benchmark, final layouts (node 0, 16 cores, 233 MB working set):

| kernel | bpw | max err vs ggml ref | streaming GB/s | cache-resident GB/s |
|---|---:|---:|---:|---:|
| Q4_K x16 | 4.625 | 1.4e-4 | 92.3 | 316 |
| Q5_K x16 | 5.625 | 1.4e-4 | 94.1 | 320 |
| Q6_K x16 | 6.562 | 1.2e-4 | 98.4 | 356 |
| Q8_0 x16 | 8.500 | 1.8e-4 | 99.5 | 643 |

The first Q5_K/Q6_K versions streamed at 84/70 GB/s: runtime-indexed accumulator arrays
spilled to the stack and qs/qh lived in separate streams. Named accumulators and one
sequential stream per block fixed both.

Dev-model chains (8-layer, tok/s medians): prod 44.4 | spin 46.4 | +shexp 48.3 |
+fused 52.5 | +qa 54.9/56.0 (qa invalid until the strided-row fix). 4-layer oracle:
x16 experts / x16 q8_0 = 0.0000 logprob diff vs base (bit-exact); attn requant q6_K
0.022, q5_K 0.020; shexp split 0.0000; qa (pre-fix) 0.25.

Chains and logs live in `/dev/shm/glm-dev/chain*.log`; per-run probes in
`/dev/shm/glm-dev/results/probe-*.json`.

## Host isolation effect (2026-09-01 23:29, same v4 server before/after)

| arm | raw tok/s mean | range |
|---|---:|---|
| v4 before isolation | 6.30 | 5.70-6.50 |
| v4 after `isolate-background.sh` | **6.56** | 6.53-6.64 |

Isolated v4 MTP n2/p0: 8.67 mean (7.28-10.64, acc 0.67); pre-isolation arm 8.81 (7.54-10.67) - within acceptance noise.

Run-queue wait across all llama-server threads during the isolated arm: 5.8% of run time
(was 93% in the ACTIVE-policy failure; not measured on the unisolated v4). With the
background load confined, the remaining wait is self-contention between the target and
draft contexts, whose pools share cores; the dispatch threads now spin hard for 300 us and
then poll with sched_yield (`GGML_CPU_NUMA_DISPATCH_HARD_SPIN_US`).
