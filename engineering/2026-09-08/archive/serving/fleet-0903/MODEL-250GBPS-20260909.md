# Feasibility of 250 GB/s per model

September 9, 2026. The user asks whether each model can sustain 250+ decimal
GB/s. Using the stated approximately 380 GB/s server capacity, 250 GB/s is
65.79%. Assess one active request stream with the whole server available to
its compute workload; permanent simultaneous residency with Full is not a
requirement. The reference measurements below are historical completed runs,
not a newly executed three-model benchmark or a hardware ceiling proof.

## Measured distance from the target

| Model and measured configuration | Generated tok/s | Adjusted decode GB/s | Bandwidth increase needed to reach 250 |
| --- | ---: | ---: | ---: |
| GLM-5.3-Flash Q8_0, latest raw stack, two runs of both workloads | 11.42-11.49 | 234.52-237.10 | 5.4-6.6% |
| GLM-5.3-Flash Q8_0, earlier MTP2 batching trial | 13.60-14.78 | 205.36-210.04 | 19.0-21.7% |
| GLM-5.3 Full, current Q4-based mixed runtime, MTP2 | 7.89-9.64 | 196.67-199.02 | 25.6-27.1% |
| Qwen3.8-Flash-Next UD-Q6_K_XL, Q8 draft, MTP4, private shared-dispatch stack, two runs of both workloads | 23.27-30.47 | 134.99-146.22 | 71.0-85.2% |

The Qwen range combines prose and code; prose measured 23.27-23.28 tok/s at
134.99-135.47 GB/s, while code measured 29.67-30.47 tok/s at 140.92-146.22
GB/s. Code exceeded 30 tok/s only once. This experimental stack has not been
promoted to the selected service. Flash's MTP2 trial predates the latest raw
kernel stack, which still needs an MTP2 measurement.

These bandwidth values come from system-wide memory-controller counters
inside stable streamed decode windows, with adjacent idle traffic subtracted.
Attribution is therefore an estimate. The examined GLM records have complete
48-counter measurements, valid decode windows, and no guard aborts. The
Qwen comparison validates all eight bandwidth windows and exact outputs and
draft counts across its two off/on pairs. None of these results reaches
250 GB/s. GLM samples exhausted their token limits during reasoning; they
measure generation speed, not completed-answer latency or task quality.

My assessment is that Flash raw decode is the closest and most plausible
candidate, Full is a credible but unproven stretch, and Qwen needs a much
larger improvement whose feasibility is not established. The percentage
increase in the table is arithmetic on bandwidth, not a guaranteed speedup.
Low utilization alone does not prove that the unused bandwidth is accessible
to the model's current execution pattern.

## What has to improve

Whole-model decode includes matrix arithmetic, routing, state updates, draft
processing, and synchronization. Hardware memory capacity does not establish
that every stage can use its bandwidth ceiling. This is consistent with
[Intel's CPU roofline guidance](https://www.intel.com/content/www/us/en/docs/advisor/get-started-guide/2023-0/identify-bottlenecks-using-cpu-roofline.html),
which separates compute and memory limits and explicitly notes that not every
loop can use the machine's maximum capabilities.

The completed current Qwen operation trace assigns about 58% of target graph
stage time to matrix operations and 11-12% to cross-socket reductions. Its
draft output projection accounts for about 49% of draft graph time. These
are summed socket-stage timings with following barriers included, not
recoverable fractions of request wall time. They identify concrete areas
for investigation but do not justify forecasting a 71-85% bandwidth gain.
The preceding shared-dispatch model pairs produced only 0.12-3.45% speed
changes across workloads and repeats.

For Flash, the useful next comparison is the retained improved Q8 kernels
with MTP2, followed by controlled synchronization experiments. Full needs
fresh whole-model validation of kernel and synchronization improvements.
Qwen needs evidence of larger gains in target matrix execution, draft output
projection, and cross-socket scheduling. Repeating earlier unsuccessful
barrier or spinning changes without new evidence is not an established path.

Generation speed and quality remain part of acceptance. Flash MTP already
generated about 14.78 tok/s at 210.04 GB/s, while its improved raw mode
generated about 11.49 tok/s at 237.10 GB/s. Higher bandwidth alone does not
make the model faster. Preserve Flash's near-lossless quality requirement
and Qwen's higher-precision target; Q8 itself is not a completed source-model
quality evaluation. Repeated fresh prose and code measurements must pair
useful generated tok/s with actual decode bandwidth.

Qwen3.8-27B remains a retained fallback in the model-choice inventory. This
assessment has no comparable recent whole-server IMC baseline for it and
does not assign it a supported 250 GB/s forecast.
