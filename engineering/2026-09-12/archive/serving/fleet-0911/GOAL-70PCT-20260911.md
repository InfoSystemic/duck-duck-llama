# Goal: >70% of 380 GB/s and high tok/s on all four models — 2026-09-11

Short answer: **70% (266 GB/s) is not reachable from configuration on any of the four models,
and the reason is now measured rather than assumed.** Every byte-side lever is already
correct; the entire deficit is *duty cycle* — the fraction of decode spent inside the matmul
kernels — and nothing in the knob space moves it. What would move it is a graph-level
reduction in op count, which is an engine project with an uncertain payoff (s.24 of
`FLEET-EXTRACTION-20260911.md`).

## 1. The denominator is real (this had never been checked)

Measured node-local streaming-read ceiling: **381.6 GB/s** — 82.6% of the 460.8 GB/s
theoretical from 24 DIMMs at 2400 MT/s across 4 sockets. So "380" is right within 0.4%, and
70% = **266 GB/s** is an honest target. Hyperthreading adds nothing (381.7 vs 380.5); 8
cores/socket already reach 87% of the 16-core figure.

No model reaches 70%. The best utilisation measured all session is **63.4%**
(GLM-5.3-Flash, speculation off, with both implemented fixes), and the best single-stream
throughput is **19.90 tok/s** (Qwen, pinned production config). Nothing achieves both.

**Prefill is not a way round it.** Prompt processing runs batch-512 with huge ops, so it
looked like the high-duty-cycle regime. Measured: 3,173 tokens at 62.6 tok/s and
**74.1 GB/s — 19.5% of 380**, far *below* decode. Prefill is compute-bound GEMM that reads
each weight once for many tokens, so it is the *worst* regime for bandwidth, not the best.
Decode is and remains the high-bandwidth regime.

## 3. Why it is duty cycle, and nothing else

`GB/s = 381 x (fraction of decode spent inside GEMV)`. Each term on the byte side checks out:

- **Kernels are not the limit.** Calling the *production* `ggml_gemv_q4_K_x16_q8_K` directly
  on node-local buffers reaches **277.2 GB/s at 15 threads/socket — 92% of the 301.2 GB/s a
  bare AVX-512 read loop achieves at the same thread count and moment.** `repack.cpp` has
  zero prefetch intrinsics and needs none.
- **Traffic is not wasteful.** GLM-5.3-Flash moves **14.6 GB per generated token** against a
  **14.5 GB ideal** computed from its GGUF inventory. No mirror tax to reclaim — its experts
  are 95% of the model and are split *by expert* across sockets.
- **NUMA placement is perfect**: 43.3 / 43.8 / 42.8 / 43.4 GB/s per socket.
- **TLB is 1.2%** of cycles; huge pages are neutral.
- Decode is *partial rate, steadily* — the in-window stall fraction is ~3%, and only 3.9% of
  decode exceeds 300 GB/s.

Where the time goes (perf, no call graph, fired only while a request was in flight):
**GEMV 42.9%, libgomp barrier/idle ~33%, other ops ~24%** (spread over hundreds of tiny ops).
That 33% is *straggler* time, not barrier protocol: swapping in a barrier that is **1.5x
slower** in isolation changed throughput by **0%**.

## 4. Everything tried, and what it did

| lever | result |
|---|---|
| host isolation (~4.5 cores of unpinned load penned) | **the one real win: +5% and clean measurements** |
| custom spin barrier | 0% |
| `OMP_WAIT_POLICY=active` / `GOMP_SPINCOUNT` | **catastrophic, ~250x slower** |
| threads 12 vs 15 | -4.5% |
| huge pages (`AnonHugePages` 0 -> 189 GB) | neutral |
| parallel all-reduce threshold | neutral |
| speculation depth 1 | -36% tok/s |
| concurrency C=8 | **+61% aggregate tok/s, but utilisation falls 52% -> 45%** |
| speculation off (Qwen) | **+35% utilisation, -17% tok/s** |

## 5. The two criteria genuinely fight — now shown on two models independently

Same model, same engine, same env, speculation on vs off:

| model | spec off | spec on |
|---|---|---|
| **GLM-5.3-Flash** | 12.82 tok/s @ **62.7%** | 15.20 tok/s @ 58.5% |
| Qwen3.8-Flash-Next | 16.43 tok/s @ **47.7%** | 19.90 tok/s @ 35.4% |
| DeepSeek-V4-Flash | 10.71 tok/s @ **51.0%** | 11.29 tok/s @ 40.5% |

It holds on all three runnable models, in the same direction every time.

Speculation converts DRAM traffic into tokens — Qwen 11.03 -> 6.76 GB per generated token,
DeepSeek 18.1 -> 13.6. Batching does the same more strongly (GLM-5.3-Flash C=8: +61%
aggregate tok/s, utilisation 52% -> 45%). **Optimising the percentage directly rewards
waste.** Treat tok/s as the goal and utilisation as a diagnostic.

Note the trade is far better on Qwen (+21% tok/s for -26% utilisation) than on DeepSeek
(+5.4% tok/s for -21% utilisation) — DeepSeek's DSpark draft at 52-60% acceptance is barely
paying for itself, which is worth revisiting separately.

## 6. The two models that could not be measured, and exactly why

**GLM-5.3 (Full)** — **the blocker is architecture support, not memory** (see FLEET-EXTRACTION
s.48). The current fleet runtime *denies* `glm-dsa` tensor-split (`LLM_ARCH_GLM_DSA` is in
`llm_arch_supports_sm_tensor`'s denylist), so the load aborts in 0.19 s. The older
`engines/llama.cpp-sr950-glm/build-dev2` binary allows it and is the one named in Full's own
pinned config. Memory is a *secondary* constraint and does **not** require unmounting the Flash
tmpfs — a skewed `--tensor-split 1.41,1.43,1.43,1.00` absorbs node 3's excess. Running it needs
~40 min with the Flash server down, which the permission classifier correctly gated.
Historical note: only one variant exists, `UD-Q4_K_XL` at **436 GB**, with a
documented ~628 GB load peak. Against 755 GB of RAM with **259 GB already in tmpfs**
(186 GB of which is the live GLM-5.3-Flash Q4 payload volume), that does not fit: 628 + 259 =
887. Loading it **requires unmounting the production Flash model's tmpfs**, costing a ~50
minute, 186 GB re-stage. That is a production decision, so this session did not take it; the
7.9-9.6 tok/s / ~198 GB/s figures in circulation are inherited from an earlier date when Full
was resident, not re-measured. Note it also cannot reach 20 tok/s at *any* duty cycle: at
22.55 GB per generated token it would need **451 GB/s against a measured 381 GB/s wall**.

**DeepSeek-V4.1-Flash** — runs today only as the PyTorch reference (1.24-1.30 tok/s, capped
at 1.87 even with both GEMMs instant). The llama.cpp port runs layers 0-3 and 8; the full 40
layers still need cross-layer KV sharing (only layers [2,8,14,20] own a compressor). Its
checkpoint has never been downloaded: 510 GB total, **306 GB minimum** for a speed run, with
**6.9 GB free on `/models` and 6.7 GB on `/`**. `/dev/shm`'s 306 GB of free space is not
additive — using it also requires giving up the Flash tmpfs. Its sibling **DeepSeek-V4-Flash**
(same `deepseek4` graph, same engine, same TP rules) is the honest proxy and is measured above.

## 6b. The silent-failure class (generalised with the [client] session)

**A pinned model config is the binary AND the env AND the flags. Substituting any one is a
SILENT change.** Two independent instances in one hour:

| substituted | symptom |
|---|---|
| hand-curated "minimal" env | loads, serves, **correct answers**, **8.33 vs 19.90 tok/s** |
| `LD_LIBRARY_PATH` collapsed to one dir | all symbols resolve; two layered private builds silently unused |
| pinned env dropped + TP flags removed | serves; `/completion` returns `////////////////////` |
| wrong engine for the arch | **loud**: `unknown model architecture: 'qwen4exp'` |
| GLM env given to Qwen | **loud but late**: `GGML_ASSERT(n_experts <= 256)` after a full 160 GB load |

Only the last two are obvious. Detector: test with raw `/completion` on a trivial factual
prefix, not `/chat` (a broken kernel and a broken chat template look identical through chat),
**and check the rate against a known figure** — correct output at half speed is the failure
mode no single request reveals.

## 6c. Standing rule that came out of an incident: `mpol=interleave` on RAM payload volumes

**Mount any tmpfs holding model weights with `mpol=interleave`, or stage it under
`numactl --interleave=all`.** Free up front; expensive afterwards.

Without it tmpfs places pages **first-touch**, so a 186 GB payload ends up skewed onto
whichever node staged it — the GLM Q4 volume carries 94.7 GB on node 3 against ~54.5 GB on
each of the others. **This is invisible until two models need that node**, because the
tensor-parallel loader uses a strict per-node `mbind()`: the allocation fails on one node
while the box reports 318 GB free, and the kernel OOM-kills whichever model loaded last.
It did exactly that to the production server today. `free -g` structurally cannot show it —
use `numastat -m` / `numactl -H | grep free`. `drop_caches` does not help either; shmem is not
reclaimable page cache.

Full detail and the cost of fixing the *existing* volume in s.27.

## 7. Recommendation

1. **Keep the production configs.** GLM-5.3-Flash's is already optimal — an exhaustive,
   drift-controlled sweep moved nothing. Qwen's pinned `qwen-flash-20tps.json` recipe is worth
   **2.4x** over a hand-assembled env (19.90 vs 8.33 tok/s); never rebuild that env by hand.
2. **Apply the host isolation permanently.** ~4.5 cores of unpinned desktop/daemon load
   (ChatGPT 176%, dockerd, containerd, Paseo, Thunderbird) was taxing every tensor-parallel
   token. `host-setup/isolate-background.sh` exists but had never been applied and predates
   the current offenders.
3. **Pick the criterion per workload, not per model.** For interactive serving use
   speculation and accept ~35-58% utilisation; for batch throughput use concurrency (C=8 gives
   **29.3 tok/s aggregate** on GLM-5.3-Flash); to maximise the *percentage*, turn speculation
   off — but that is optimising for waste.
4. **If 70% is genuinely required, the target is the dense matmul path — now measured.**
   The decode graph is **7,239 nodes**, and `MUL_MAT` accounts for **2,049 of them (~44 per
   layer) at only 66 us average**, carrying 31.5% of in-op time. By contrast the 378 expert
   matmuls (`MUL_MAT_ID`) average 466 us and are already well batched, and the ~4,800
   elementwise/norm nodes are 66% of the node count but just 27.6% of the time (~4% of it in
   barriers). **Batching those 44 small per-layer matmuls into a few large ones is the only
   lever found that is big enough to matter**; the elementwise-fusion idea targets a ~4%
   prize. 44 per layer is the signature of a path decomposed per-head or per
   hyper-connection stream (`hyper_connection.count=4`). Use the private-build harness
   (`fleet-0903/build_flash_q8_r8_ordered_k_0908.py`), which proves byte-identical relinking
   before swapping a single object. Payoff is unproven.
5. **Adopt `mpol=interleave` for every future RAM payload volume** (s.6c). Free, and it
   prevents the OOM class that took production down today.
6. **Three decisions belong to the maintainer.** Two trade the live Flash model for an experimental one:
   re-staging RAM to measure GLM-5.3 Full, and downloading 306 GB to attempt DeepSeek-V4.1.
   The third is whether to **schedule** a re-stage of the Q4 payload volume with
   `mpol=interleave` (s.27) so GLM-5.3-Flash and the client-portal assistant can be co-resident
   at all. Recommended as scheduled maintenance, not as an urgent fix — nothing needs the
   assistant before Monday, and the re-stage window leaves a live model's only copy partially
   downloaded.
